## 安装与配置

gstack 已安装至 `.claude/skills/gstack/`，所有技能已通过符号链接注册至 `.claude/skills/`。

### 激活 `/browse` 技能（可选）

`/browse` 需要 [Bun](https://bun.sh/) 运行时来构建浏览器二进制文件：

```bash

curl -fsSL https://bun.sh/install | bash

# 2. 构建 browse 二进制
cd .claude/skills/gstack && ./setup
```

> 其他所有技能（20+）无需 bun，可直接使用。

### 升级 gstack

```
/gstack-upgrade
```

## 开发流程总览

gstack 是一个**有序的开发流程**，每个阶段的输出会直接传递给下一个阶段：

```
Think → Plan → Build → Review → Test → Ship → Reflect
  ↓        ↓       ↓       ↓       ↓      ↓       ↓
office- plan-  （编码） review   qa    ship   retro
hours  reviews
```

### 一个完整 Sprint 约需 30 分钟

1. `/office-hours` — 明确需求，重构问题框架
2. `/plan-ceo-review` — 产品战略评审
3. `/plan-eng-review` — 技术架构设计
4. 编写代码
5. `/review` — 代码审查，自动修复明显问题
6. `/qa` — 浏览器自动化测试
7. `/ship` — 创建 PR 并发布

## 专业技能详解

### 思考阶段

#### `/office-hours` — 产品顾问

**使用时机：** 开始任何新功能之前

**作用：** 像 YC Office Hours 一样，通过六个强制性问题重构你的产品思路。不接受你的原始框架，而是倾听你的痛点并给出更精准的定位。

**输出：** 自动生成设计文档 `DESIGN.md`，供后续所有技能读取。

```
你说：想做一个"每日简报 App"
它说：不，你在构建的是一个"个人 AI 首席助理"
      [列出你没意识到的 5 个功能需求]
      [挑战 4 个前提假设]
      [给出 3 个实现方案及工作量预估]
```

---

### 计划阶段

#### `/plan-ceo-review` — CEO/创始人视角

**使用时机：** 对任何功能想法进行战略评审

**作用：** 从产品战略层面审查计划，找出隐藏在请求中的"10 星产品"。提供四种模式：扩展、选择性扩展、保持范围、缩减。

#### `/plan-eng-review` — 工程架构师

**使用时机：** 锁定技术方案

**作用：** 生成数据流图（ASCII 图表）、状态机、错误路径、测试矩阵。强迫隐藏假设浮出水面，输出详细测试计划。

#### `/plan-design-review` — 高级设计师

**使用时机：** 计划阶段的设计评审

**作用：** 对每个设计维度评分（0-10），说明满分看起来是什么样，然后编辑计划以达到最高分。检测"AI 垃圾设计"。

#### `/design-consultation` — 设计合伙人

**使用时机：** 从零构建完整设计系统

**作用：** 研究同类产品，提出安全选项和创意风险，生成真实产品 Mockup，输出 `DESIGN.md`。

---

### 执行阶段

#### `/review` — Staff 工程师

**使用时机：** 任何代码变更后，合并前

**作用：** 发现通过 CI 但会在生产炸掉的 bug。自动修复明显问题，标记完整性缺口。

**示例输出：**
```
[AUTO-FIXED] 2 个问题已修复
[ASK] 发现竞态条件 → 等待你确认修复方案
```

#### `/investigate` — 调试专家

**使用时机：** 遇到 bug 需要定位根本原因

**作用：** 系统性根因调试。铁律：没有调查就没有修复。追踪数据流，测试假设，3 次修复失败后停止并上报。

---

### 测试阶段

#### `/qa` — QA 负责人

**使用时机：** 功能开发完成后

**作用：** 打开真实浏览器，点击真实页面，发现并修复 bug，为每个修复自动生成回归测试。

**用法：**
```
/qa https://your-staging-url.com
/qa  （如果已在 DESIGN.md 中配置了 URL）
```

#### `/qa-only` — QA 报告员

**使用时机：** 只想要 bug 报告，不想自动修复

**作用：** 与 `/qa` 相同的测试方法论，但只报告不修改代码。

#### `/browse` — QA 工程师（需要 bun）

**使用时机：** 需要浏览器操作但不想全套 QA 流程

**作用：** 真实 Chromium 浏览器，真实点击，真实截图。约 100ms 每条命令。

---

### 发布阶段

#### `/ship` — 发布工程师

**使用时机：** 准备发布

**作用：** 同步主干、运行测试、审计测试覆盖率、推送代码、创建 PR。如果没有测试框架，自动搭建。一条命令完成所有发布操作。

#### `/document-release` — 技术写作

**使用时机：** 发布后

**作用：** 更新所有项目文档，自动发现过时的 README 并同步。

---

### 回顾阶段

#### `/retro` — 工程经理

**使用时机：** 每周回顾

**作用：** 团队感知的周度回顾，按人统计代码行数、提交数、测试健康度、成长机会。

## 强力工具

| 技能 | 用途 |
|------|------|
| `/codex` | **第二意见** — 通过 OpenAI Codex CLI 进行独立代码审查。三种模式：审查（通过/失败门控）、对抗性挑战、开放咨询 |
| `/careful` | **安全防护** — 在危险命令（rm -rf、DROP TABLE、force-push）前发出警告。说"be careful"激活 |
| `/freeze` | **编辑锁定** — 将文件编辑限制在一个目录内。调试时防止意外修改范围外的文件 |
| `/guard` | **最高安全** — `/careful` + `/freeze` 组合。生产环境操作推荐 |
| `/unfreeze` | **解锁** — 移除 `/freeze` 边界 |
| `/gstack-upgrade` | **自更新** — 升级到最新版本，检测全局与本地安装，显示变更内容 |

## 典型工作流示例

### 新功能开发

```bash
# 1. 明确需求
/office-hours
> 描述你想构建的功能

# 2. 策略评审（可选）
/plan-ceo-review

# 3. 技术架构
/plan-eng-review

# 4. 进入计划模式，Claude 编写代码...

# 5. 代码审查
/review

# 6. 浏览器测试
/qa https://localhost:3000

# 7. 发布
/ship
```

### Bug 修复

```bash
# 1. 系统性调查
/investigate
> 描述 bug 现象

# 2. 修复后审查
/review

# 3. 验证
/qa
```

### 生产环境操作（高风险）

```bash
# 启用最高安全模式
/guard

# 进行操作...

# 完成后解锁
/unfreeze
```

## 并行开发

gstack 支持同时运行 10-15 个并发 Sprint（不同功能、不同分支、不同 Agent）。

**并行工作示例：**
- 终端 1：`claude` → `/office-hours` 讨论功能 A
- 终端 2：`claude` → `/review` 审查功能 B 的代码
- 终端 3：`claude` → `/qa` 测试功能 C

这是实现"每天 10,000+ 行可用代码"的关键机制。

## 注意事项

### 本项目特定规则

1. **网页浏览必须使用 `/browse`**，严禁使用 `mcp__claude-in-chrome__*` 工具
2. `/browse` 需要先安装 bun 并运行 `./setup` 构建浏览器二进制
3. 所有计划和文档继续使用中文（本项目 CLAUDE.md 规定）

### 技能读取顺序

每个技能会自动读取前序技能的输出文档：
- `DESIGN.md` — `/office-hours` 输出，供所有后续技能读取
- `PLAN.md` — `/plan-eng-review` 输出，供 `/qa` 读取测试计划

### 更新 gstack

gstack 代码在 `.claude/skills/gstack/`，已从项目 git 中排除（有独立的 `.git`）。运行 `/gstack-upgrade` 更新，或手动 `git pull`。
