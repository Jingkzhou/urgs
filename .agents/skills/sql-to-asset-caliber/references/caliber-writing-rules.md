## 1. SQL 模式到业务语言的转换

| SQL 证据 | 业务口径需要表达的内容 |
| --- | --- |
| `WHERE` / `HAVING` | 纳入、排除对象及阈值条件 |
| `CASE WHEN` | 业务分类、优先级和兜底规则 |
| `JOIN` | 需要补充的业务属性或约束关系；不能仅写“关联某表” |
| `GROUP BY` | 一行数据的统计粒度 |
| `SUM/COUNT/AVG/MAX/MIN` | 指标聚合方式、对象范围和单位 |
| `COUNT(DISTINCT ...)` | 去重对象和唯一性口径 |
| `ROW_NUMBER/RANK` | 最新、首笔、优先记录或排名选择规则 |
| `UNION ALL` | 业务来源范围合并，保留重复 |
| `UNION` | 业务来源范围合并并去重 |
| `COALESCE/NVL` | 空值替代及其业务含义 |
| 常量投影 | 固定分类、来源或状态；必须核对值域 |
| 日期函数 | 统计日期、账期、观察窗口和截止时点 |
| 算术表达式 | 指标计算关系、单位和异常处理 |
| 码值转换 | 正式码值含义和转换后的业务分类 |

只写 SQL 能证明且业务人员需要理解的规则。临时 CTE 名、别名、函数实现和执行优化细节保留在“技术证据”，不要进入业务口径正文。

## 2. 表级口径结构

建议写成一个短段落，依次覆盖：

1. **业务对象与用途**：该表沉淀什么对象，用于什么分析、报送或管理；
2. **数据粒度**：一行代表一个什么对象在什么日期、机构或其他维度下的记录；
3. **数据范围**：来源系统和核心纳入、排除条件；
4. **加工原则**：关键关联、汇总、去重、最新记录和时间规则；
5. **监管关系**：对应哪些已确认监管表、监管主题或口径。

不要在表级口径中逐个罗列所有字段。只有影响整表含义的字段规则才需要出现。

## 3. 字段与指标口径结构

普通字段建议按以下顺序写：

1. 业务含义；
2. 来源或生成方式；
3. 适用范围和时间口径；
4. 分类、码值、空值和默认规则；
5. 必要的例外情况。

指标字段还应补充：

- 统计对象与粒度；
- 聚合方式；
- 分子、分母或计算公式；
- 去重键；
- 统计周期和截止时点；
- 单位、精度、正负号；
- 除零、空值和冲销等异常处理。

如果某项从 SQL 或监管资产无法确认，写入待确认项，不在正文中补造。

## 4. 文风和内容边界

- 面向业务和数据治理人员，使用自然、完整的中文句子。
- 优先写“纳入正常状态的贷款合同”，不要写“`status = '1'`”；正式码值可在括号中保留作为证据。
- 避免“取某表某字段”“通过 CASE 判断”等纯技术句式；说明它代表的业务规则。
- 一条字段口径通常控制在 1 至 4 句话；复杂指标可以分点。
- 不使用“显然”“应该”“大概”等模糊词。证据不足统一进入“待确认”。
- 不照抄监管描述；结合目标 SQL 说明监管定义在目标资产中的具体使用方式。

## 6. 简短示例

SQL 证据：目标字段 `normal_loan_balance` 为贷款余额求和，但只纳入有效合同且五级分类属于监管码表中的“正常”或“关注”；数据按统计日期和机构汇总。

不合格写法：

> 对 status 等于 1 且 five_class in 01,02 的 balance 做 sum，并按 data_date、org_id group by。

合格写法：

> 按统计日期和机构汇总有效贷款合同的本金余额，仅纳入五级分类为“正常”或“关注”的贷款；分类范围以监管五级分类码表的当前有效码值为准，金额单位沿用源余额字段定义。

如果 `01`、`02` 尚未通过监管码表确认，则不要写出“正常”或“关注”，改为待确认：

> SQL 使用五级分类代码 `01`、`02` 作为纳入范围，但当前未取得对应码表说明，需确认代码含义后再写回。
