# 系统入口与单点登录对接说明

## 1. 文档目的

本文档用于指导外部子系统与监管报送一体化系统（以下简称 `URGS`）进行系统入口和单点登录对接，重点说明：

- 对方系统需要提供给 `URGS` 的信息
- `URGS` 需要提供给对方系统的能力
- 双方联调步骤
- 当前认证规则下已支持和暂不支持的能力边界

## 2. 当前认证规则说明

根据当前系统实现，`URGS` 认证机制如下：

- `URGS` 自身登录方式为用户名/密码登录
- 登录成功后，后端签发 `token`
- 前端将 `token` 保存到浏览器 `localStorage`，后续请求通过 `Authorization: Bearer <token>` 访问
- 后端通过拦截器校验 `Bearer Token`
- 当前已内置一套简化版 `OAuth 2.0 Authorization Code` 流程，用于“用户已登录 URGS 后，跳转到其他子系统时免登录”

当前代码已支持的方向：

- 用户先登录 `URGS`
- 从 `URGS` 点击系统入口跳转到子系统
- 子系统通过 `code -> access_token -> user_info` 完成免登录

当前代码暂不支持的方向：

- 用户已登录“对方系统”，点击其首页菜单后，直接免登录进入 `URGS`
- 也就是说，`URGS` 当前更适合作为统一认证中心/授权中心，而不是作为第三方 SSO 客户端

因此，基于当前认证规则，推荐的落地模式是：

- 对方系统首页可以嵌入 `URGS` 入口菜单或链接
- 用户进入 `URGS` 后完成一次登录
- 登录 `URGS` 后，再跳转其他已接入子系统时不需要重复登录

## 3. 推荐对接模式

推荐采用“统一入口 + URGS 作为 SSO 授权中心”的模式。

### 3.1 场景一：对方系统首页嵌入 URGS 入口

对方系统在首页增加菜单或快捷入口，点击后跳转到 `URGS` 地址。

适用目标：

- 在对方系统中提供 `URGS` 统一入口
- 统一访问门户

说明：

- 该场景本身仅是“入口嵌入”
- 如果希望“点击后直接免登录进入 URGS”，当前版本暂不支持，需要后续扩展 `URGS` 作为 SSO Client 的能力

### 3.2 场景二：登录 URGS 后跳转子系统免登录

子系统接入 `URGS` 的简化版 OAuth2 对接能力，用户在 `URGS` 中点击子系统入口时，自动带上授权码，子系统完成换 token、取用户信息、建立本地会话。

适用目标：

- 用户已登录 `URGS`
- 从 `URGS` 跳转到子系统不再重复登录

## 4. 双方职责分工

### 4.1 对方系统需要提供给 URGS 的内容

对方系统接入免登录时，需要提供以下信息：

| 项目 | 说明 | 是否必填 |
| --- | --- | --- |
| 系统名称 | 展示在 `URGS` 系统入口中的名称 | 是 |
| Client ID / AppID | 子系统唯一标识 | 是 |
| 回调地址 `callbackUrl` | `URGS` 授权成功后回跳地址 | 是 |
| 网络区域 | 内网/专线/互联网等 | 建议 |
| 协议类型 | 当前建议填写 `OAuth 2.0` | 是 |
| 系统图标 | 用于工作台入口展示 | 建议 |
| 系统状态 | 正常/维护/停用 | 建议 |
| 联调联系人 | 技术负责人及联系方式 | 是 |
| 测试环境地址 | 测试联调用 | 是 |
| 生产环境地址 | 上线后用 | 是 |

如果需要完成“免登录跳转”，对方系统还需要具备以下能力：

- 能接收 `URGS` 回跳时携带的 `code`
- 能从对方系统服务端调用 `URGS` 的 `token` 接口
- 能从对方系统服务端调用 `URGS` 的 `user_info` 接口
- 能根据 `URGS` 返回的用户信息建立本地登录态
- 能处理首次登录用户的本地用户映射策略

### 4.2 URGS 需要提供给对方系统的内容

`URGS` 需要向对方系统提供以下内容：

| 项目 | 说明 |
| --- | --- |
| `URGS` 访问地址 | 门户访问地址，供首页菜单跳转 |
| 系统注册能力 | 在 `URGS` 系统管理中维护子系统名称、Client ID、回调地址等 |
| 授权码签发能力 | 用户登录 `URGS` 后，为目标子系统生成 `code` |
| Token 交换接口 | 子系统通过 `code` 换取 `access_token` |
| 用户信息接口 | 子系统根据 `access_token` 获取用户身份信息 |
| 联调支持 | 配置测试系统、配合联调和问题排查 |

## 5. 接口说明

以下为当前代码已实现的接口能力。

### 5.1 URGS 登录接口

`POST /api/auth/login`

请求体：

```json
{
  "username": "zhangsan",
  "password": "******"
}
```

返回示例：

```json
{
  "token": "xxxxxx",
  "id": "1",
  "empId": "zhangsan",
  "name": "张三",
  "roleName": "管理员",
  "roleId": 1,
  "system": "URGS"
}
```

说明：

- 此接口用于用户登录 `URGS`
- 登录成功后，前端保存 `token`

### 5.2 URGS 跳转子系统接口

`POST /api/system/{id}/jump`

请求头：

```http
Authorization: Bearer <urgs_token>
```

返回示例：

```json
{
  "targetUrl": "https://sub-system.example.com/callback?code=xxxxx"
}
```

说明：

- 用户已登录 `URGS` 时调用
- `URGS` 根据目标系统配置生成 `code`
- 后端返回最终跳转地址

### 5.3 OAuth 授权码接口

`POST /api/oauth/authorize`

请求体：

```json
{
  "client_id": "AML_SYS_PROD",
  "redirect_uri": "https://sub-system.example.com/callback",
  "response_type": "code"
}
```

返回示例：

```json
{
  "code": "xxxxx",
  "redirect_uri": "https://sub-system.example.com/callback"
}
```

说明：

- 当前接口用于已登录 `URGS` 用户生成授权码
- 常见使用方式有两种：
  - `URGS` 前端登录页带 `client_id`、`redirect_uri` 参数时，登录后自动调用
  - 已登录 `URGS` 的门户内，点击子系统入口时由后端生成授权码

### 5.4 Token 交换接口

`POST /api/oauth/token`

请求体：

```json
{
  "grant_type": "authorization_code",
  "code": "xxxxx"
}
```

返回示例：

```json
{
  "access_token": "xxxxxx",
  "token_type": "Bearer",
  "expires_in": 7200
}
```

说明：

- 子系统拿到 `code` 后，通过服务端调用此接口
- 当前有效期为 `7200` 秒

### 5.5 用户信息接口

`GET /api/oauth/user_info`

请求头：

```http
Authorization: Bearer <access_token>
```

返回示例：

```json
{
  "id": 1,
  "empId": "zhangsan",
  "name": "张三",
  "orgName": "科技部",
  "roleName": "管理员"
}
```

说明：

- 子系统获取到用户信息后，应自行完成本地会话创建

## 6. 对接流程

## 6.1 首页嵌入 URGS 入口流程

1. 对方系统提供首页菜单位置和展示名称
2. `URGS` 提供门户访问地址
3. 对方系统在首页配置菜单或快捷入口
4. 用户点击入口后跳转到 `URGS`

建议菜单示例：

- 菜单名称：监管报送一体化系统
- 打开方式：新页签或当前页
- 跳转地址：`URGS` 门户地址

说明：

- 该流程只解决“入口嵌入”
- 不自动解决“从对方系统免登录进入 URGS”

## 6.2 登录 URGS 后跳转子系统免登录流程

1. 对方系统向 `URGS` 提供 `clientId`、`callbackUrl`、系统名称等信息
2. `URGS` 在系统管理中注册该子系统
3. 用户登录 `URGS`
4. 用户在 `URGS` 工作台点击目标子系统入口
5. `URGS` 生成授权码 `code` 并拼接到回调地址
6. 浏览器跳转到对方系统回调地址
7. 对方系统服务端使用 `code` 调用 `URGS /api/oauth/token`
8. `URGS` 返回 `access_token`
9. 对方系统使用 `access_token` 调用 `URGS /api/oauth/user_info`
10. 对方系统拿到用户信息后建立本地登录态
11. 用户进入对方系统首页，无需再次输入账号密码

## 7. 联调前准备

双方在联调前需要准备以下内容。

### 7.1 对方系统准备项

- 提供测试环境地址
- 提供生产环境地址
- 提供 `clientId`
- 提供回调地址 `callbackUrl`
- 完成回调页或回调接口开发
- 完成服务端换 token 接口开发
- 完成用户信息获取和本地登录态建立逻辑
- 明确用户唯一标识映射规则，建议使用 `empId`

### 7.2 URGS 准备项

- 在系统管理中录入子系统信息
- 开通测试环境访问
- 提供接口文档和报文样例
- 配合验证 token、user_info 返回内容
- 提供联调联系人

## 8. 联调步骤

建议按以下步骤联调。

### 第一步：基础连通性验证

- 验证对方系统回调地址可访问
- 验证 `URGS` 到对方系统网络连通
- 验证对方系统到 `URGS` 接口网络连通

### 第二步：系统注册

- 在 `URGS` 系统管理中新增子系统配置
- 核对 `clientId`
- 核对 `callbackUrl`
- 核对状态是否为启用

### 第三步：授权码回跳验证

- 用户登录 `URGS`
- 点击目标子系统入口
- 检查是否正确跳转到：

```text
{callbackUrl}?code=xxxxx
```

- 检查 `code` 是否成功生成

### 第四步：Token 交换验证

- 由对方系统服务端调用 `URGS /api/oauth/token`
- 检查是否返回 `access_token`
- 检查返回时效 `expires_in`

### 第五步：用户信息验证

- 由对方系统调用 `URGS /api/oauth/user_info`
- 核对以下字段是否正确：
  - `id`
  - `empId`
  - `name`
  - `orgName`
  - `roleName`

### 第六步：本地登录态验证

- 对方系统根据用户信息创建本地会话
- 验证用户是否成功进入子系统首页
- 验证关键菜单、角色和权限是否符合预期

### 第七步：异常场景验证

- `code` 失效场景
- 未登录 `URGS` 直接跳转场景
- 回调地址配置错误场景
- 用户不存在场景
- 用户禁用场景
- Token 过期场景

## 9. 用户标识与映射建议

建议以 `empId` 作为跨系统统一用户标识。

建议规则如下：

- `URGS` 返回 `empId`
- 对方系统优先按 `empId` 找本地用户
- 若本地不存在，按双方约定策略处理：
  - 自动创建只读账号
  - 拒绝登录并提示联系管理员
  - 建立用户映射表后再开放

## 10. 安全与生产建议

当前代码可支撑联调和原型验证，但若用于正式生产，建议补充以下能力：

- 将 `token` 和 `code` 存储从内存改为 `Redis`
- 支持多节点部署下的共享会话
- 为 `/api/oauth/token` 增加 `client_secret` 校验
- 增加授权码有效期与重复使用防护说明
- 增加 `refresh_token` 机制
- 增加单点退出或统一登出机制
- 增加来源校验、签名校验和访问白名单
- 增加审计日志，记录发码、换 token、取用户信息全过程

## 11. 结论

基于当前认证规则，可以先落地以下目标：

- 对方系统首页嵌入 `URGS` 入口链接或菜单
- 用户登录 `URGS` 后，跳转已接入子系统时不需要再次登录

基于当前认证规则，暂不能直接落地以下目标：

- 用户在“对方系统已登录”的情况下，点击菜单后免登录进入 `URGS`

如果后续要实现“从其他系统直接免登录进入 URGS”，需要新增“`URGS` 作为 OAuth Client / SSO Client”能力，单独设计入站单点登录方案。
